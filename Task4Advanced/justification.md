# Обоснование событийного подхода

## Сравнение: текущий подход vs событийная архитектура

| Критерий               | Текущий подход (Camel ESB + DWH)                  | Целевой подход (Kafka + Event-Driven)                    |
|------------------------|---------------------------------------------------|----------------------------------------------------------|
| **Интеграция**         | Точка-точка через ESB, синхронные вызовы          | Асинхронные события, подписчики не зависят от издателей  |
| **Масштабирование**    | Монолитное DWH — вертикальный scale-up            | Горизонтальный scale-out, независимые домены             |
| **Time-to-market**     | Часы на отчёт, месяцы на новую интеграцию         | Минуты на отчёт, дни на подключение нового домена        |
| **Связанность**        | Сильная (все зависят от DWH)                      | Слабая (домены независимы)                               |
| **Отказоустойчивость** | Отказ DWH = остановка всех систем                 | Отказ домена не влияет на остальные                      |
| **Эволюция**           | Изменение схемы DWH = миграция всех потребителей  | Схема события версионируется, обратная совместимость     |
| **Аналитика**          | Batch-загрузка в DWH, трансформации занимают часы | Потоковые витрины, near-real-time                        |

## Преимущества событийного подхода для «Будущее 2.0»

### 1. Гибкость
- **Новые бизнес-направления** (фарма, электроника) подключаются через подписку на существующие события без изменения ядра
- **Новый продукт** = новый домен, который слушает нужные топики Kafka
- Пример: фармкомпания подписывается на `PrescriptionCreated` для анализа эффективности лекарств

### 2. Масштабируемость
- **Георасширение**: Kafka MirrorMaker реплицирует события между регионами
- **Рост данных**: ClickHouse шардируется горизонтально
- **Пиковые нагрузки**: Kafka буферизует события, потребители масштабируются независимо

### 3. Скорость реакции
- **Отчётность**: с часов до минут (потоковые витрины ClickHouse)
- **Интеграция**: с месяцев до дней (подписка на события вместо точечной интеграции)
- **Диагностика**: врач получает результат ИИ-анализа через секунды после запроса

### 4. Независимость доменов
- Команда Медицины не ждёт команду Финтеха для релиза
- Отказ CRM не блокирует создание приёмов
- Каждый домен выбирает свой стек (Go, Java, Python)

### 5. Аудит и прослеживаемость
- Все события сохраняются в Kafka (retention = 30 дней)
- Data Lake хранит полную историю событий
- Возможность восстановить состояние системы на любой момент времени

## Почему отказываемся от Camel ESB

| Проблема Camel ESB                               | Решение Kafka                                      |
|--------------------------------------------------|----------------------------------------------------|
| Маршрутизация «точка-точка», нет истории событий | Сохранение событий в топиках, replay при сбоях     |
| Синхронные вызовы блокируют отправителя          | Асинхронная публикация, back-pressure              |
| Сложность добавления новых потребителей          | Любой сервис может подписаться на топик            |
| Нет встроенной обработки ошибок                  | Dead Letter Queue для проблемных сообщений         |
| Масштабирование ограничено                       | Горизонтальное масштабирование брокеров и партиций |

## Почему отказываемся от DWH как интеграционного слоя

| Проблема DWH                          | Решение Data Mesh + Kafka                 |
|---------------------------------------|-------------------------------------------|
| Монолит — единая точка отказа         | Распределённая архитектура                |
| Бизнес-логика в хранимых процедурах   | Логика в доменных сервисах                |
| Batch-окна — задержка в часах         | Потоковая обработка — задержка в секундах |
| Сложность добавления новых источников | Новый источник = новый топик Kafka        |
| Конфликты при параллельной разработке | Независимые домены                        |
