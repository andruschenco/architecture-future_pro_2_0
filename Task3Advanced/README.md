## C4-диаграммы

### Уровень контейнеров (Container Diagram)

Файл: [c4-diagram-container.drawio](c4-diagram-container.drawio)

На диаграмме контейнеров показана целевая архитектура всей системы «Будущее 2.0»:

```
Пользователи → API Gateway → Доменные сервисы → Event Bus (Kafka) → Data Layer
→ Legacy Bridge
```

**Контейнеры системы:**

| Контейнер                  | Технология                         | Назначение                                              |
|----------------------------|------------------------------------|---------------------------------------------------------|
| API Gateway                | Kong / Yandex API Gateway          | Аутентификация, авторизация, маршрутизация              |
| Домен «Медицина»           | Go/Java-микросервисы + PostgreSQL  | Clinic, EHR, Inventory, Staff                           |
| Домен «Финтех»             | Go/Java-микросервисы + PostgreSQL  | Core Banking, Payments, Credit, Compliance              |
| Домен «ИИ-сервисы»         | Python-микросервисы + GPU-ноды     | ML Models, Image Analysis, NLP                          |
| Домен «Клиенты и партнёры» | Java-микросервисы + PostgreSQL     | CRM, Customer 360, Contracts                            |
| Event Bus                  | Apache Kafka                       | Асинхронный обмен событиями, Schema Registry, DLQ       |
| Data Lake                  | S3 / Yandex Object Storage         | Хранение сырых, обработанных и анонимизированных данных |
| Analytics Engine           | ClickHouse + Trino                 | Потоковые витрины, федеративные запросы                 |
| Data Portal                | DataHub + Apache Superset          | Self-Service BI, Data Catalog, Report Builder           |
| Legacy Bridge              | Camel ESB + SQL Server (read-only) | Антикоррупционный слой на время миграции                |

### Уровень компонентов (Component Diagram)

Файл: [c4-diagram-medical-component.drawio](c4-diagram-medical-component.drawio)

Детально показан домен «Медицина»:

| Компонент                  | Назначение                                                   |
|----------------------------|--------------------------------------------------------------|
| Clinic Service             | Запись на приём, расписание, пациентский поток               |
| EHR Service                | Медицинская история, диагнозы, назначения                    |
| Inventory Service          | Оборудование, медикаменты, складские остатки                 |
| PostgreSQL                 | Транзакционная БД со схемами clinic, ehr, inventory          |
| Event Publisher (Debezium) | Публикация изменений в Kafka                                 |
| Anti-Corruption Layer      | Чтение из старого DWH → маппинг → Kafka (на период миграции) |

**Потоки данных:**
1. Врач создаёт приём → Clinic Service → Kafka `medical.appointments`
2. Fintech читает `medical.appointments` → создаёт счёт → Kafka `fintech.invoices`
3. ИИ-сервис читает `medical.diagnoses` → анализирует → Kafka `ai.results`
4. Data Lake потребляет все топики → ClickHouse Data Marts
5. Аналитик строит отчёт через Data Portal → Trino → ClickHouse

## Описание ключевых изменений

### Что уходит (легаси)

| Система                             | Причина отказа                               | Замена                                   |
|-------------------------------------|----------------------------------------------|------------------------------------------|
| SQL Server 2008 DWH                 | End of Life, не масштабируется, монолит      | Data Lake (S3) + ClickHouse              |
| PowerBuilder                        | Несовместим с облаком, дорог в поддержке     | Веб-интерфейсы в каждом домене           |
| Apache Camel ESB                    | Не поддерживает потоковую аналитику и replay | Apache Kafka                             |
| Монолитная BI (Power BI поверх DWH) | Часы на формирование отчётов                 | Self-Service портал (Trino + ClickHouse) |

### Что появляется

| Система               | Назначение                                           |
|-----------------------|------------------------------------------------------|
| Доменные микросервисы | Изоляция бизнес-логики по направлениям               |
| Apache Kafka          | Центральная событийная шина                          |
| Data Lake (S3)        | Единое хранилище с зонами Raw → Curated → Anonymized |
| ClickHouse            | Потоковые витрины и аналитика near-real-time         |

### Текущие направления (год 0)

- Финтех-услуги (банк)
- ИИ-сервисы (диагностика)

### Новые направления (горизонт 3 года)

| Направление                               | Интеграция                                             | Домен                                         |
|-------------------------------------------|--------------------------------------------------------|-----------------------------------------------|
| **Фармацевтические компании**             | Данные о лекарствах, поставках, клинических испытаниях | Новый домен «Фарма»                           |
| **Производитель медицинской электроники** | IoT-события с устройств, телеметрия                    | Новый домен «IoT»                             |
| **Новые регионы (2–3)**                   | Локальные требования, геораспределённые данные         | Репликация доменов с локальными особенностями |

### Как архитектура поддерживает масштабирование

- **Новый домен** → подключается к Kafka без изменений в существующих доменах
- **Новый регион** → георепликация Kafka (MirrorMaker 2) + локальные инстансы ClickHouse
- **Новый источник данных** → новый топик Kafka + конвейер в Data Lake
- **Новый продукт** → новый микросервис в соответствующем домене

## Ключевые архитектурные решения

### 1. Переход от монолита к Data Mesh
- **Было:** Единое DWH (SQL Server) со всей бизнес-логикой
- **Стало:** Доменные сервисы + Event Bus (Kafka) + Data Lake + Self-Service BI

### 2. Событийно-ориентированная архитектура
- Домены взаимодействуют только через события в Kafka
- Слабосвязанность позволяет развивать направления независимо
- Сохраняется целостное представление по ключевым показателям через Data Lake

### 3. Принципы безопасности
- Медицинские карты и результаты исследований **не включаются** в витрину данных
- Деперсонализация на уровне ingestion (перед попаданием в Data Lake)
- Шифрование at rest (KMS) и in transit (TLS)
- Audit logging всех операций с медицинскими и финансовыми данными
- Разграничение доступа на уровне колонок (Apache Ranger)

### 4. Миграционная стратегия (Strangler Fig)
- Параллельная работа старого DWH и нового Data Lake (6 месяцев)
- Anti-Corruption Layer для совместимости с Camel ESB
- Постепенный вывод легаси из эксплуатации по этапам
