# Миграция функций ESB в целевую архитектуру

## Замечание
Apache Camel ESB выполняет критичные интеграционные функции, которые не покрываются простой заменой на «голую» Kafka. 
Kafka — это транспорт и хранилище событий, но не выполняет валидацию, сложные трансформации, оркестрацию долгих процессов и не предоставляет готовые паттерны надёжности. 
Эти обязанности должны быть явно переданы другим компонентам.

## Карта миграции функций

| Функция ESB (Camel)                                           | Куда переезжает                                           | Компонент                                                                | Обоснование                                                                                     |
|---------------------------------------------------------------|-----------------------------------------------------------|--------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| **Валидация сообщений и ФЛК**                                 | Schema Registry + продуценты                              | Confluent/Apicurio Schema Registry, доменная валидация перед публикацией | Форматная валидация (Avro/Protobuf) на стороне реестра схем; бизнес-правила в сервисе-источнике |
| **Пакетные трансформации (ETL)**                              | DBT + Spark (batch)                                       | DBT поверх Data Lake (S3), Apache Spark для сложных преобразований       | Трансформации выполняются на уровне данных, а не в интеграционном слое                          |
| **Потоковые трансформации**                                   | Kafka Streams / ksqlDB                                    | Kafka Streams API или ksqlDB                                             | Обогащение, фильтрация, агрегация, join потоков в реальном времени                              |
| **Маршрутизация (включая content-based)**                     | Топики Kafka + Consumer Groups + Kafka Streams `branch()` | Топики как адреса, группы потребителей как получатели                    | Каждый домен подписывается на свои топики; сложная маршрутизация через branching в Streams      |
| **Паттерны надёжности (retry, circuit breaker, idempotency)** | Dead Letter Queue + Resilience4j + Idempotent Producer    | Топики `*.dlq`, библиотеки устойчивости в потребителях                   | Повторная обработка, изоляция сбоев, гарантии exactly-once                                      |
| **Оркестрация процессов (саги)**                              | Process Manager (Saga Pattern)                            | Отдельный Kafka Streams-сервис с state store                             | Управление распределёнными транзакциями, компенсирующие события                                 |
| **Логирование и аудит интеграций**                            | OpenTelemetry + Data Lake                                 | Трейсинг через Kafka headers, архив событий в S3                         | Полная прослеживаемость цепочек событий                                                         |
| **Мониторинг интеграций**                                     | Prometheus + Grafana + Kafka Exporter                     | Kafka Metrics API, Consumer Lag мониторинг                               | Замена JMX-мониторинга Camel                                                                    |

## Детали реализации

### 1. Валидация и ФЛК
- **Форматная валидация**: Schema Registry проверяет совместимость схемы при публикации (backward/forward compatibility).
- **Бизнес-валидация**: выполняется в продуценте (доменном сервисе) до отправки в Kafka.
- **Ошибки валидации**: сообщения, не прошедшие проверку, направляются в `*.invalid` топик.

### 2. Трансформации
- **Простые преобразования** (обогащение, фильтрация) — Kafka Streams.
- **Сложные преобразования** (агрегации, оконные функции) — ksqlDB или Spark Structured Streaming.
- **Пакетные ETL** — DBT поверх Data Lake (S3), запускается по расписанию.

### 3. Маршрутизация
- **Каноническая маршрутизация**: выбор топика по типу события.
- **Content-based routing**: Kafka Streams `branch()` разделяет поток по условиям.
- **Подписчики**: Consumer Groups читают только свои топики, обеспечивая изоляцию.

### 4. Надёжность
- **Retry**: настраивается в потребителе (Spring Retry, Resilience4j) с экспоненциальной задержкой.
- **Dead Letter Queue**: отдельный топик `*.dlq` с retention = 30 дней.
- **Circuit Breaker**: в API Gateway и межсервисных вызовах (Resilience4j).
- **Идемпотентность**: включённый idempotent producer в Kafka и дедупликация по ключу.

### 5. Оркестрация
- **Saga Pattern**: каждая бизнес-операция разбивается на последовательность событий.
- **Process Manager**: Kafka Streams-приложение, отслеживающее состояние саги в state store.
- **Компенсация**: при ошибке публикуются компенсирующие события.

### 6. Аудит и мониторинг
- Каждое событие содержит заголовки с trace ID, источником и временем.
- Все события сохраняются в Data Lake (S3) для последующего анализа.
- Метрики потребителей (Consumer Lag, throughput) экспортируются в Prometheus.


## Выводы
Замена Camel ESB требует разворачивания  полноценного **Integration Layer** из пяти компонентов: Schema Registry (валидация), Kafka Streams (трансформации и маршрутизация), DBT/Spark (пакетные ETL), Process Manager (оркестрация), Dead Letter Queue (надёжность). Это обеспечит полное покрытие функций, которые ранее выполняла шина.
